# Next vertical slice (3D-7): "Sound, Save and Sign-off" - the horizontal slice's last layer

> **Status:** plan - not started. Builds on slice 3D-6 ("Into the Barrow", `docs/SLICE_BARROW.md`), which made the
> GDD's horizontal slice playable from title to title. GDD: `docs/GDD_Horizontal_Slice.pdf` (v1.0); "GDD 15.4" refers to
> its sections, "plan 3D-6 5.11" to `docs/NEXT_SLICE_BARROW.md`. Decisions marked **Recommendation** stay open until
> the project owner confirms them (§12). Every KOS API named here must be checked against the installed KOS headers
> before it is used (the user's DreamSDK reports KOS 2.3.0; this repository has no KOS tree, only stub headers).

**Goal:** finish the GDD's horizontal slice **to its definition of done** (GDD 18). After this slice, the game **sounds**
like a game (music for every mode, sound effects for every action the player takes), **remembers** the player (VMU
save, CONTINUE on the title, options, the cleared crest across power cycles), has the console's **frame**
(boot splash, pause menu, controller-removal pause, soft reset), and is **signed off on real hardware**: every scene
measured in milliseconds on a Dreamcast, 60 fps with audio and saving running, the GDD's verification table (GDD 17)
complete, and the documentation the GDD's definition of done lists.

> The Dreamcast logo fades, a two-second studio card, and the title's dusk orbit starts **with its theme**. The menu
> now reads **CONTINUE** (greyed until there is a save), **NEW GAME**, **OPTIONS**, **CREDITS**; moving the cursor
> clicks, confirming chimes. Hollowmere has a village tune; Wren's text blips as it types; a sword swing whooshes and
> lands with a crack of bone **on the frame the sparks fly**. At Wren's checkpoint a small VMU icon spins in the corner:
> "Saving...". Start pauses the field (RESUME / OPTIONS / RETURN TO TITLE); pulling the controller pauses too. The
> barrow's night theme fades in through T7's black; the Warden's name card lands with a sting; the boss theme plays
> under the fight; the death screen has its own sting; the dawn has a theme of its own, and the credits roll over
> music. Power off, power on: CONTINUE is lit, and the crest is still under the logo.

In GDD milestone terms this is **H7 (polish and sign-off)** plus the GDD's **audio track (R1, R2, G5)** and its
stretch goals **VMU save (15.4, G4)** and **pause menu (4)**, with the optional **boot splash (3)**. Nothing in the
game's rules, maps or scripts changes, except a few script commands that start sounds (§5.6).

### 2.2 Gaps that shape the plan

| # | Gap | Consequence |
|---|---|---|
| G1 | No audio path on the Dreamcast at all (no `snd_*` call anywhere) | the engine is new code (Stage A); the hooks already mark the moments |
| G2 | Main RAM holds the whole romdisk (the `.elf` embeds it) | every second of music costs main RAM; the music budget is set by §8, not by taste |
| G3 | Battle sounds fire at **rule resolution** (`battle.cpp:159-163`), while the 3D sequence shows the impact 20-60 ticks later | a swing heard before it is seen; they must move to `battle3d.cpp`'s cue ops (S4) |
| G4 | `text_blip` fires every 3rd character; with B held (4x) that is up to 80 blips per second | needs a rate limit (at most one per 3 ticks) and a voice cap |
| G5 | Up to 4 game ticks run per displayed frame after a hitch: a burst of events in one frame | the audio layer collects events per frame, deduplicates and caps them (§5.2) |
| G6 | No persistence: the crest, options and progress die with the power | S5-S7 |
| G7 | Start does nothing in the field; a controller pulled mid-game is ignored | S8 |
| G8 | "No heap after boot" (TD3 of 3D-6) vs KOS's VMU calls, which allocate internally (`vmufs_read` returns a `malloc`ed buffer; `vmu_pkg_build` allocates) | the rule is restated for the save worker: bounded, freed in the same call, net zero (§5.3) |
| G9 | The romdisk image is not rebuilt when only a file inside a subfolder changes (KOS's `romdisk.img` rule); `make rm-elf && make` is needed after editing `romdisk/maps/lights.txt` | audio iteration will hit this constantly: fix the makefile first (task A0) |
| G10 | `tests/dialog/run.sh`, `tests/battle3d/run.sh`, `tests/vs1art/run.sh`, `tests/run_tests.sh` are not executable (run them with `bash`) | chore: `chmod +x` (task A0) |
| G11 | The slice-3D-6 night look was tuned on the host renderer and was too dark on the user's display; it was fixed in data (`romdisk/maps/lights.txt`, `docs/barrow/night_brightness.jpg`) | lesson: anything visual or audible is tuned on the device early (Stage 0, F-tasks) |

### 2.3 The `.elf` constraint, in numbers

The Dreamcast has 16 MiB main RAM, 8 MiB VRAM and **2 MiB sound RAM** (the AICA's, shared by its ARM7 driver, the
samples and the stream buffers). The `.elf` carries the romdisk, so the romdisk lives in main RAM. Today: romdisk
3.01 MB (after the UI art pass, `docs/UI_ART.md`), a 1,792 KiB model arena, ~480 KiB portrait cache and the rest of the BSS (the host build's BSS is 6.1 MB,
`size build/battle_trace_f32`; the SH4 figure is measured in Stage 0). Roughly 5-6 MiB of main RAM is free (**to be
confirmed by Stage 0's RAM line**). Mono 22,050 Hz ADPCM costs 10.8 KiB per second, so **one minute of music is
~650 KiB of main RAM** whether it plays or not. That sets the music budget (§8): about 3 minutes of music in total (§7.2).

## 4. Player-facing design

### 4.1 Boot

| Step | Ticks | Content |
|---|---|---|
| BIOS | - | the Dreamcast logo (not ours) |
| Splash (S9) | fade in 20, hold 80, fade out 20 | black, a small studio card (2D text from the dialog font, or a logo texture); A/Start skips after tick 30; the audio and the VMU scan start **underneath** it (§5.2, §5.3) |
| Load | under the splash | today's boot (`game_boot`) + `audio_boot` + the VMU scan (read the save, if any) |
| T1 | 45 | the title as today, **with the title theme fading in over the same 45 ticks** |

The splash hides the load: the boot must not show a black screen longer than today's. If the load outlasts the splash,
the splash holds (never a blank screen).

### 4.2 Title menu (S6)

CONTINUE / NEW GAME / OPTIONS / CREDITS; the box grows from 240x88 to 240x132 (4 items x 22 px + padding). The cursor
starts on **CONTINUE if it is enabled, else NEW GAME**. CONTINUE greyed = not selectable (the cursor skips it) with a
one-line reason under the box (SA6). NEW GAME with an existing save asks nothing (the save is overwritten at the first
checkpoint, C0): **Recommendation** (D6). Sounds: `menu_move`, `menu_confirm`, `menu_cancel` (B closes the menu back to
PRESS START), `menu_denied` (A on a greyed item, if the cursor is ever allowed on one).

CONTINUE: T2's black (30), then the checkpoint's map fades in (20) with the hero on the checkpoint tile, full HP, the
objective and the markers of the saved stage: **byte for byte the state a death retry at that checkpoint produces**
(SA1). If the checkpoint is C3 (the waystone) the boss ring is as a retry leaves it (the short intro on entry).

### 4.3 Options (S7)

| Item | Values | Default | Note |
|---|---|---|---|
| MUSIC | 0-10 | 8 | left/right changes; a music preview plays at the new level |
| EFFECTS | 0-10 | 10 | a `menu_move` plays at the new level |
| SOUND | STEREO / MONO | the BIOS setting (`flashrom_get_syscfg`, §13.1) | MONO centres every pan |
| BACK | - | - | B also backs out; changes are kept in RAM and saved with the next save |

A screen of its own from the title (T-fade 12 + 12 over the title's orbit) and an overlay from the pause menu.

### 4.4 Pause (S8)

* **Start in the field** (mode Field, no transition running, no script running) opens a translucent overlay (the
  death screen's box style): PAUSED, RESUME / OPTIONS / RETURN TO TITLE. Start or B resumes. RETURN TO TITLE asks
  "Return to the title? Progress since the last checkpoint is lost." YES / NO (NO preselected), then T11.
* While paused: no game tick runs (`game_tick` is not called for the field; the pause menu has its own tick), the
  music ducks to 50 %, the results card's clock stops. **Determinism:** pausing must not change any trace line other
  than the pause's own (a test runs a route with and without pauses and compares).
* **Controller removed** (no controller on port A at a poll, in any mode that takes input): in the field, pause; in a
  dialog, battle or menu, a "Please reconnect the controller" overlay that freezes the game tick until a controller is
  back; then a fresh press is needed (`input_reset`). Not in the attract demo (it returns to the title).
* **Soft reset**: A+B+X+Y+Start held together for 1 frame (the Dreamcast convention) = T11 to the title from any mode,
  progress since the last checkpoint discarded. It never exits to the BIOS / loader (KOS's defaults must not take
  over; §13.1).

### 4.5 Saving (S5)

| When | What is saved | Indicator |
|---|---|---|
| `checkpoint` (C0 at NEW GAME's first field tick, C1, C2, C3, Brom's rest) | the checkpoint's Progress, stats, options, meta | VMU icon + "Saving..." top right for the write's duration, at least 45 ticks |
| the results card (E6) | `cleared = 1`, best time/rank, the stats; the checkpoint fields reset to "none" (a finished game has nothing to continue: **Recommendation** D7) | same |
| leaving OPTIONS (if changed) | options | same |

Never during: a transition's swap, the T9 slow motion, or twice at once (a save requested while one runs is queued;
only the latest snapshot is written). The game **never waits** for a save. The player is told once per power-on if
saving is off:

| Situation | Message (once, on the title under the menu, or as a 3 s toast in the field) | Game continues |
|---|---|---|
| No VMU at boot | "No VMU found. Progress will not be saved." | yes |
| VMU full (needs 2 blocks) | "Not enough free blocks (2 needed). Progress will not be saved." | yes |
| Write failed / VMU pulled while saving | "Save failed." | yes; the next checkpoint tries again |
| Save damaged (CRC / version / size) | CONTINUE greyed, "Save data damaged." | yes; the next save overwrites it |
| VMU inserted later | the next save finds it (the worker rescans on each request) | yes |

### 4.6 Sound design

**Music follows the transition catalogue.** One music stream at a time; every change rides a catalogued transition,
so the fades in §4.6.1 are the transitions' own tick counts. The same track continuing across a transition is not
restarted (the village -> dialog -> village; the barrow after a retry keeps playing if it was already playing).

#### 4.6.1 Music map

| Moment | Transition | Music |
|---|---|---|
| Boot -> title | T1 (45) | `title` fades in over 45, loops |
| Title -> new game | T2 (30 + 15 + 90 + 30) | `title` fades out over the first 30; the card is silent (or a wind bed: could); `village` fades in with the intro's 30 |
| Field <-> dialog | T3 / T4 | the music ducks to 60 % under the box (12 ticks down, 12 up) |
| Field -> battle | T5 (8 + 24) | the field track's **position is remembered**; cut at the first white flash under a `battle_start` whoosh; `battle` (or `boss`) starts with the battle's fade-in |
| Battle -> field (win) | `sting_victory` over the VICTORY banner (one-shot on the stream), then T6 (24 + 12) | the field track **resumes from the remembered position**, fading in over T6's 12 |
| Battle lost | T9 | the battle track slows with the 0.5x (a pitch drop is optional: could) and fades over T9's 30; `sting_death` at the tint; the death screen is silent after it |
| Retry | T6 (30 + 20) | the field track from its start, fading in over 20 |
| Map change | T7 (20 + 20) | out over 20 with the black, the new map's track in over 20 (village <-> barrow) |
| Boss intro | T8 (script) | `barrow` fades out over the crane's first 60 ticks; `sting_boss_name` with the name card; silence under the three lines (the boss theme starts with T5) |
| Boss won -> ending | T10 (48 + 40) | `boss` cut at the white flash; `sting_victory` ; `dawn` from the white, through the gathering |
| THE END, credits | (script) | `credits` (or `title`, §7.2) fades in with THE END's card |
| Results -> title, death -> title | T11 (60) | fade out over 60; then T1's title theme |
| Pause | - | duck to 50 % |
| Attract demo | (title idle) | the title theme continues under the demo (the demo's own sounds play at 50 %) |

#### 4.6.3 Mixing rules

* Levels (0-255 at full options): music 170, effects 220, blips 90, stings 200. The options scale them (0-10 -> 0-100
  %, a squared curve so the steps sound even).
* Ducking: dialog 60 %, pause 50 %, the name card's sting ducks the music to 40 % for its length.
* Voices: at most **8 effect voices** at once; a new effect takes a free voice, else replaces the oldest voice of the
  **same cue**, else the oldest voice of a **lower priority** (priority per cue in the table, §6.1), else it is dropped.
  Deterministic (no time-of-day, no random).
* The same cue at most once per frame (G5); each cue has a minimum repeat interval in ticks (§6.1).
* Pan: centre by default; battle cues pan by the actor's screen x (-0.6..0.6 of full) unless MONO.

## 5. Architecture

### 5.1 Modules

| Module | Kind | Responsibility |
|---|---|---|
| `src/audio.*` (new) | **pure logic**, host-testable, deterministic | loads `romdisk/audio/cues.txt`; maps event names to cue ids at boot; the music state machine (current, target, remembered position, fades, ducking, stings); the per-frame event queue (dedupe, rate limit, voice policy); produces **backend commands** |
| `src/save.*` (new) | pure logic | the save payload: build from Progress + stats + options + meta, parse, validate (magic, version, size, CRC); the VMU package header and icon bytes; no I/O |

### 5.2 Audio: the frame, the threads, determinism

```
game thread, per displayed frame:
  for each game tick (0..4):  game_tick()  ->  audio_event(name) / audio_music(...)   (queued, no backend call)
  audio_frame()  ->  dedupe + rate limits + voice policy + fades/ducking for this frame
                 ->  at most 8 backend commands: eng::snd_play / eng::snd_music / eng::snd_music_volume ...
  draw
audio poll thread (KOS only):  loop { snd_stream_poll(music); thd_sleep(~8 ms) }
```

* **The game never blocks on audio.** Backend calls are small AICA commands; the stream is refilled by its own thread,
  so music keeps playing through map loads and the boot (KOS threads are preemptive).
* **Thread safety:** the game thread writes the music request (track id, generation counter, start position) into a
  single-writer mailbox; the poll thread's stream callback reads it. No locks in the callback except a KOS mutex
  around the mailbox swap if needed. The callback hands back pointers into the track's bytes (**zero copy**: the
  romdisk is in RAM; `fs_mmap` or one boot-time read into a static buffer, §13.1).
* **Determinism:** audio never writes game state; all timing is in ticks; the host records the same commands at the same
  ticks as the Dreamcast issues them. A run with `NO_AUDIO`-equivalent host settings produces byte-identical traces
  except the `A` lines (AU-T7).
* **The file source is one function** (`audio_track_bytes(id)`): the romdisk today, a `/cd` stream in a later disc
  build.

### 5.3 Saving: the worker

```
game thread:  save_request(snapshot)   // copies <= 128 bytes into the pending slot; returns at once
              save_status()            // idle / writing / ok / failed(kind), for the indicator and the messages
VMU worker thread (KOS):  wait for a pending slot -> scan port A..D for a memory card -> build the package
              (static buffer) -> vmufs_write(..., VMUFS_OVERWRITE) -> status
```

* At boot, before T1, the worker scans and **reads** the save (under the splash): the title knows CONTINUE's state
  before it appears.
* **Heap rule (restated, G8):** no allocation on the game thread after boot (unchanged). The VMU worker may call KOS
  functions that allocate internally; each call's allocations are freed before it returns, so DIAG's heap line stays
  `+0` over a playthrough. The host counter attributes allocations inside `eng::vmu_*` to a separate bucket that must
  return to zero after every call (SV-T6).
* The package is built **by our code** into a static buffer (the VMU file format is documented in `dc/vmu_pkg.h` and
  is small): no `vmu_pkg_build` allocation, and the host can test the bytes. Compare once on hardware that the BIOS
  file manager shows the icon and the descriptions (hardware checklist).
* Maple traffic: the controller is polled every frame while the worker writes blocks; KOS's maple driver queues both.
  Verify on hardware that input never stutters during a save (checklist); fallback: save only under a fade.

### 5.4 Engine API additions (`src/engine.h`)

```cpp
// audio (backend); ids come from audio_boot's table
bool snd_boot(const AudioBank& bank);                 // load effects into sound RAM, start the stream thread
void snd_play(int sfx, int vol, int pan);             // vol 0..255, pan 0..255 (128 = centre)
void snd_music(int track, uint32_t start_sample, int vol, bool loop);   // -1 = stop
void snd_music_volume(int vol);                       // per frame during fades
uint32_t snd_music_position();                        // samples played (for the remembered position)
// VMU (backend)
void vmu_request(const uint8_t* payload, int bytes);  // non-blocking
int  vmu_status();                                    // see save.h
bool vmu_boot_read(uint8_t* payload, int* bytes);     // at boot only
// system
bool sys_mono();                                      // the BIOS's stereo/mono setting
bool pad_present();                                   // controller on port A
```

## 6. Data formats

### 6.1 `romdisk/audio/cues.txt`

```
# cue   name            kind   file                 vol  prio  min_gap  flags
music   title           loop   music/title.adp      170
music   village         loop   music/village.adp    170
music   dawn            loop   music/dawn.adp       170
sting   victory         once   music/victory.adp    200
sfx     text_blip              sfx/blip.adp          90   1     3
sfx     hit_bone               sfx/hit_bone.adp     220   5     2        pan_actor
sfx     soul_rend              sfx/soul_rend.adp    255   9     0
alias   music_credits   title                       # SA3: reuse if the budget is tight
```

Rules (checked by `tools/audio/lint_cues.py` and by the C++ loader with the same messages): every name unique; every
file exists; every event name used in `src/` (grep) and in the scripts has a cue (or is listed as `silent`); loops
have loop points; `sfx` files are at most 65,534 samples; the boot report prints the sound RAM and main RAM totals.

### 6.2 `.adp` (one sound, our own header)

| Offset | Bytes | Field |
|---|---|---|
| 0 | 4 | magic `ADP1` |
| 4 | 4 | sample rate (Hz) |
| 8 | 4 | samples |
| 12 | 4 | loop start (samples; = samples if none) |
| 16 | 4 | loop end |
| 20 | 2 | format: 0 = Yamaha ADPCM 4-bit, 1 = PCM 8-bit (`AUDIO_PCM8`) |
| 22 | 2 | channels (1) |
| 24 | 8 | CRC32 of the data + reserved |
| 32 | n | data, 32-byte aligned |

The encoder is `tools/audio/adpcm.py` (the reference); the host's C++ decoder must match it sample for sample (AU-T3).
If the installed KOS's `snd_sfx_load` only accepts WAV, the KOS backend uploads `.adp` data itself (see §13.1: mirror
`snd_sfx_load`'s upload and `snd_sfx_play_chn`'s channel command) **or** the tool also writes a WAV (format 0x14 or
PCM) for effects. Decide in task A2 after reading the installed `sfxmgr`.

### 6.3 The save (`HYMN.SYS` on the VMU, 2 blocks)

Payload (128 bytes, little-endian, `static_assert`ed like Progress):

| Offset | Bytes | Field |
|---|---|---|
| 0 | 4 | magic `HYM1` |
| 4 | 2 | payload version (1) |
| 6 | 2 | payload size (128) |
| 8 | 4 | save counter (increments each save) |
| 12 | 32 | **the checkpoint's Progress** (`progress_checkpoint()`, byte for byte) |
| 44 | 1 | has_checkpoint (0 after the results card, D7) |
| 45 | 1 | cleared (the crest) |
| 46 | 1 | best rank (0 none, 1 bronze, 2 silver, 3 gold) |
| 47 | 1 | reserved |
| 48 | 4 | best play time (ticks) |
| 52 | 28 | SessionStats at the checkpoint (7 x uint32) |
| 80 | 4 | options: music 0-10, effects 0-10, mono 0/1, reserved |
| 84 | 40 | reserved (zero) |
| 124 | 4 | CRC32 of bytes 0..123 |

The VMU package around it (the KOS `vmu_pkg_t` layout; build it ourselves, §5.3): short description "PROJECT HYMN",
long description "Hollowmere - S3 - 12:34" (stage and play time), app id "PROJECT_HYMN", one 32x32 16-colour icon
(`tools/make_vmu_icon.py` from the logo's crest, committed + reproducible), no eye-catch. 128 (header) + 32 + 512 (icon) +
128 (payload) = 800 bytes = **2 blocks**.

Loading checks in order: file present -> package header sane -> payload magic -> version (older versions: migrate or
reject with "Save data damaged"; never read garbage) -> size -> CRC -> Progress sanity (stage <= 7, map < map count,
checkpoint tile walkable on that map). Any failure = CONTINUE greyed with the reason.

### Decisions (recommendations; confirm or change)
| # | Question | Recommendation |
|---|---|---|
| D1 | Music format | **Streamed mono 22,050 Hz Yamaha ADPCM** from the romdisk via KOS `snd_stream` (ADPCM start function if the installed KOS has it; else 8-bit PCM at 16 kHz as the fallback, `AUDIO_PCM8`). No CPU-decoded formats (Vorbis, MP3): they cost frame time the game does not have |
| D2 | Music budget | <= 2.0 MiB (about 3 minutes in all); the credits alias the title theme; if this is too little, the next step is a disc build with streaming from `/cd`, not more RAM |

| D4 | Sourcing | CC0 packs + stand-ins; commission only the title, village and boss themes if the CC0 search finds nothing fitting |
| D5 | Save slots | one file, one slot; no A/B double file (2 blocks; a power loss mid-write loses only that save: the CRC detects it) |
| D6 | NEW GAME with a save | no confirmation; the save is replaced at C0 (a one-file game; the GDD has no slots) |
| D7 | After the results card | the save keeps the crest, best result and options; `has_checkpoint = 0` (CONTINUE greyed: "Cleared - start a NEW GAME") |

### Risks
| Risk | Mitigation |
|---|---|
| **ADPCM loop clicks** on the AICA (the decoder's state carries across the loop jump) | loop-state matching in the encoder (§13.2); A5's early hardware listen; fallback: PCM8 for the worst loop, or loops that end and start in silence |
| Stream underruns during loads (map change, the boot) | the poll thread (preemptive) + stream buffers sized for >= 250 ms; the DIAG underrun counter (P2) |
| G2 bus contention (sound RAM writes stall the SH4; PVR and maple share the bus) | effects uploaded only at boot; the stream refills small chunks; never `spu_memload` in a gameplay frame (§13.1) |
| KOS API differences between versions (the stubs were wrong once before) | stubs copied from the installed headers (A3); every API named here verified first; the report lists the versions |
| VMU writes interfering with controller polling | worker thread; hardware check P3; fallback: save under a fade |
| RAM: the romdisk grows by ~2.4 MB | Stage 0's RAM line first; the budget tool fails the build past the cap |
| Content licences | allowed-licence list; `SOURCES.md` checked by AU-T2; no file without an entry |
| Scope creep (more music, more menus, pitch effects) | §1.3 and the could list; anything else is a change to this plan |

## 13. Hints and pointers for the developers

### 13.1 KOS notes (verify each against `$KOS_BASE/include` of the installed KallistiOS before relying on it)

* **Sound RAM and channels.** `dc/sound/sound.h`: `snd_init`, `snd_mem_malloc` / `snd_mem_free` /
  `snd_mem_available` (sound RAM addresses, not pointers). The AICA has 64 channels; a channel's sample-count
  registers are 16-bit, which is why KOS's `snd_sfx_load` refuses samples over 65,534 and why music must **stream**.
* **Effects.** `dc/sound/sfxmgr.h`: `snd_sfx_load` (a WAV file; check whether your version takes 4-bit Yamaha
  ADPCM, format 0x14), `snd_sfx_play(handle, vol 0-255, pan 0-255)` returns the channel, `snd_sfx_play_chn`,
  `snd_sfx_stop`, `snd_sfx_chn_alloc`. Recent KOS versions add `snd_sfx_load_ex` / `snd_sfx_load_buf` and
  `snd_sfx_play_ex` (loop points, rate): check the header. Load every effect **at boot** (it allocates and reads
  files); at run time only play/stop. If you need something sfxmgr lacks, read `kernel/arch/dreamcast/sound/
  snd_sfxmgr.c` and mirror its `AICA_CMD_CHAN` packet (`dc/sound/aica_comm.h`) rather than inventing one.
* **Music.** `dc/sound/stream.h`: `snd_stream_init`, `snd_stream_alloc(callback, buffer bytes)`, `snd_stream_start`
  (16-bit PCM) and, in recent versions, `snd_stream_start_adpcm`; `snd_stream_volume`, `snd_stream_stop`,
  `snd_stream_poll`. The callback is asked for N bytes and returns a pointer + the bytes it provides: return pointers
  into the track's data (zero copy) and handle the loop wrap by returning the tail first, the head on the next call.
  `snd_stream_poll` must run often (the poll thread: `thd_create` from `kos/thread.h`, a ~8 ms sleep; check the
  `thd_create` signature of your version). The kos-ports library `libwav` also streams WAVs on a thread: reading its
  source is a good guide even if you do not link it.
* **Zero-copy track data.** Romdisk files are in RAM: `fs_mmap(fd)` (`kos/fs.h`) returns a pointer into the image for
  romdisk files (check it on `/rd`); otherwise read each track once at boot into a static buffer sized by the budget.
* **G2 bus.** Writes to sound RAM (`spu_memload`, the stream refill) go over the G2 bus, which is slow and stalls the
  CPU while it is busy. Bulk uploads (the effects) only at boot; the refill is small and steady. KOS may offer
  `spu_memload_sq` / `spu_dma_transfer` (check `dc/spu.h`).
* **Stereo/mono.** `dc/flashrom.h`: `flashrom_get_syscfg(&cfg)`; `cfg.audio` is 0 for mono, 1 for stereo (check the
  field name).
* **VMU.** `dc/maple/vmu.h`, `dc/vmufs.h`, `dc/vmu_pkg.h`: `maple_enum_type(n, MAPLE_FUNC_MEMCARD)` to find cards,
  `vmufs_free_blocks(dev)`, `vmufs_read(dev, name, &buf, &size)` (allocates `buf`: free it), `vmufs_write(dev, name,
  data, size, VMUFS_OVERWRITE)`. `vmu_pkg_t`'s layout defines the header (short/long descriptions, app id, icon
  count, palette, data length, CRC). File names are at most 12 characters. Writes take a noticeable fraction of a
  second: only ever on the worker thread.
* **Controller presence and the reset combo.** `maple_enum_type(0, MAPLE_FUNC_CONTROLLER)` returns NULL when port A
  is empty (the input code already calls it each frame: `platform/kos/main.cpp:178`). Check whether the installed KOS
  registers a default A+B+X+Y+Start handler (`cont_btn_callback`) that exits; if it does, replace it with ours (D8).
* **PVR error events** (task 0C): `dc/asic.h` defines ASIC events for the PVR's ISP/TSP/OPB out-of-memory and TA
  input errors; `asic_evt_set_handler` can count them. Check first whether KOS's own PVR code already hooks them (do
  not replace a handler KOS needs).

### 13.2 ADPCM loop seams (the one audio problem worth planning for)

The AICA's ADPCM decoder keeps its predictor (value and step) across a loop jump, so a loop encoded naively starts its
second pass with the wrong state and clicks. In the encoder: encode the loop body, take the decoder state at the loop
end, re-encode the body **starting from that state**, and repeat until the end state matches the start state (it
converges in a few passes for musical material); then the stream's wrap is seamless. Prefer loop points at zero
crossings in quiet passages. AU-T3 checks the state match on the host; A5 checks it by ear on hardware **before** the
content pass. For streams, the same applies to the stream's own buffer wrap only if the data is not contiguous: the
callback hands the decoder one continuous byte sequence, so only the musical loop point matters.

### 13.3 Build and workflow

* **Romdisk staleness (A0).** KOS's `romdisk.img` rule does not track files inside subfolders. Add to the makefile:
  `romdisk.img: $(shell find $(KOS_ROMDISK_DIR) -type f)` (a prerequisite-only rule; the recipe stays KOS's). Until
  then: `make rm-elf && make` after any romdisk edit (this is what the night-brightness fix needed).
* **Stub headers** (`tests/dialog/kos_stub`): extend them with exactly the prototypes the new backend uses, copied
  from the installed KOS. The first DreamSDK build of an earlier slice failed on a stub that guessed a type
  (`docs/NEXT_SLICE.md`, T1).
* **Long commands:** the host suites take 5-10 minutes; run them in the background and poll the log (an agent's tool
  call times out at 300 s). Do not edit `src/` or `platform/` while a suite is building.
* **Tools with Blender / the VS1 converter** are not needed in this slice; the audio tools need only Python 3 + NumPy
  (keep it that way: no ffmpeg at build time; decode the sources once with whatever you like and commit WAVs to
  `assets/audio/src`).

### 13.5 Conventions the tests enforce (unchanged from 3D-6)

* **Determinism:** ticks and integers in logic; float == double for every route; presentation clocks never feed back
  into rules. Audio and saving are presentation/persistence: they read the game, never write it (except CONTINUE,
  which goes through `checkpoint_restore`).
* **No heap after boot** on the game thread (host counter + DIAG).
* **Budgets are checked by the suites**; a new screen is not done until a `--path` sweep measured it.
* **Assets are reproducible**; generated files have a rebuild check.
* **Every deviation from the GDD** carries a `# slice 3D-7` comment (scripts) or a row in the report.

### 13.6 Lessons from slice 3D-6

* **Tune on the device early.** The night preset looked right in the host renderer and was too dark on the user's
  screen; it was a one-line data fix only because it was data. Audio levels and loop seams are the same kind of
  problem: A5 puts a cue player on hardware before any content work.
* **Data over code** paid off (lights, maps, scripts, transitions): keep cues, levels, music per map and the options'
  defaults in data.
* **Sweep everything that moves the camera or adds overlays** (`--path title|credits` found the title and credits
  costs); add `--path pause` / `options` for the new 2D screens.
* **The transitions are the seams**: the load hitches (map change, title) happen under black; keep the audio and VMU
  work there or on threads, never in a visible gameplay frame.
* **Kill switches per risky hardware feature** (`NO_FOG`, `GROUND_NO_VQ`, ...) made remote triage possible; do the
  same for audio and the VMU (§5.5) and list them in TRIAGE on day one.
